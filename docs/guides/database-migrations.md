# Гайд по миграциям базы данных

Документ предназначен для разработчиков и агентов, которые изменяют схему PostgreSQL в `uptime-app`.

## Где находятся миграции

- Приложение backend: `backend/`.
- SQL-файлы: `backend/migrations/`.
- Команда запуска: `backend/cmd/migrate/main.go`.
- Локальный PostgreSQL: `backend/docker-compose.yml`.
- Строка подключения: `DATABASE_URL`.

Каждая миграция состоит из пары файлов с одинаковым номером и именем:

    backend/migrations/000004_short_description.up.sql
    backend/migrations/000004_short_description.down.sql

`up.sql` применяет изменение, `down.sql` описывает обратное изменение. Номер должен быть следующим по порядку; текущая последняя миграция — `000003`.

## Перед началом работы

1. Убедитесь, что меняется схема, а не только код. Для таблиц, колонок, индексов, ограничений и расширений нужна новая миграция.
2. Прочитайте модели и репозитории, использующие изменяемые таблицы: `backend/internal/models/` и соответствующий пакет в `backend/internal/`.
3. Проверьте рабочее дерево: не перезаписывайте чужие изменения и не редактируйте уже применённую миграцию.
4. Запустите локальную базу:

       cd backend
       docker compose up -d
       export DATABASE_URL='postgres://uptime:uptime@localhost:5436/uptime?sslmode=disable'

## Создание миграции

1. Выберите следующий шестизначный номер и короткое имя в `snake_case`.
2. Создайте пару `.up.sql` и `.down.sql` в `backend/migrations/`.
3. Пишите SQL явно и безопасно: сохраняйте ограничения, внешние ключи и индексы; учитывайте существующие данные; не удаляйте данные без отдельного согласования.
4. Проверьте, что `down.sql` удаляет только объекты, добавленные этой миграцией.
5. Если нужно преобразовать существующие данные, по возможности разделите перенос данных и удаление старой структуры на отдельные этапы.
6. Обновите код backend, если меняется контракт модели или репозитория.

Пример:

    -- 000004_add_last_checked_at.up.sql
    ALTER TABLE monitors ADD COLUMN last_checked_at TIMESTAMPTZ;

    -- 000004_add_last_checked_at.down.sql
    ALTER TABLE monitors DROP COLUMN last_checked_at;

## Применение

Команду запускают из `backend/`, потому что источник задан как `file://migrations` относительно текущего каталога:

    cd backend
    go run ./cmd/migrate

Команда требует `DATABASE_URL`, применяет ещё не применённые `up.sql` по порядку и успешно завершается, если изменений нет.

В текущем проекте `cmd/migrate` поддерживает только применение вперёд (`Up`). Не запускайте `down.sql` вручную в общей или production-базе. Для отката согласуйте отдельный план; обычно безопаснее написать новую forward-миграцию.

## Проверка результата

Проверяйте миграцию на чистой и на уже существующей базе:

1. Убедитесь, что PostgreSQL готов: `docker compose ps`.
2. Повторно запустите `go run ./cmd/migrate` из `backend/`. Команда должна завершиться без новых изменений.
3. Проверьте таблицу версий:

       psql "$DATABASE_URL" -c 'SELECT version, dirty FROM schema_migrations;'

   Ожидаются последняя применённая версия и `dirty = false`.
4. Проверьте изменённые объекты, например `psql "$DATABASE_URL" -c '\d+ monitors'`. Для индексов и ограничений используйте `\di` и `\d`.
5. Запустите из `backend/`:

       go test ./...
       go build ./...

   PostgreSQL-интеграционные тесты выполняются при заданном `TEST_DATABASE_URL`:

       TEST_DATABASE_URL="$DATABASE_URL" go test ./...

6. Проверьте затронутый API или пользовательский сценарий. Для переноса данных отдельно проверьте старые записи, новые записи и повторный запуск приложения.

## Проверка на чистой базе

Для локальной базы можно пересоздать volume и применить весь набор миграций:

    cd backend
    docker compose down -v
    docker compose up -d
    go run ./cmd/migrate

`docker compose down -v` удаляет локальные данные PostgreSQL без возможности восстановления из этого volume. Выполняйте команду только если локальные данные больше не нужны.

## Ошибки и dirty-состояние

- Если база недоступна, проверьте `docker compose ps`, `DATABASE_URL`, порт `5436` и логи контейнера.
- Если в `schema_migrations` указано `dirty = true`, остановитесь и выясните, какие изменения успели примениться. Не исправляйте версию или dirty-флаг вслепую.
- Не редактируйте миграцию, которая уже могла попасть в окружение. Создайте новую миграцию, исправляющую состояние.
- Перед восстановлением зафиксируйте ошибку, текущую версию схемы и фактически применённые изменения.

- [ ] SQL учитывает данные, внешние ключи, индексы и обратимость.
